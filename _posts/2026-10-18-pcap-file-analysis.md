## 1. 개발한 프로그램 정보

PCAP 파일에 저장된 패킷을 순서대로 읽고, 헤더 정보와 프로토콜별 통계를 출력하는 프로그램을 개발했다. 이를 통해 패킷의 구조를 이해하고 어떤 통신이 발생했는지 해석하는 것을 목표로 했다.

>실제 코드 작성은 ai에게 맡기고, 개념 이해와 결과 분석에 집중했다.

|항목|내용|
|---|---|
|실행 환경|Windows 11, Python 3.13.3|
|사용 라이브러리|dpkt 1.9.8|
|검증 도구|TShark 4.6.9|
|지원 범위|classic PCAP 2.4, Ethernet II, 조각화되지 않은 IPv4, TCP·UDP·ICMP|
|출력 정보|MAC·IP 주소, 해당되는 포트 번호, 프로토콜, TCP 플래그, ICMP Type·Code, 패킷별 정보와 통계|

## 2. PCAP과 패킷 구조 이해

### 2-1. PCAP와 패킷
**패킷** : 송수신 정보와 전달할 데이터가 들어있는 통신 단위이다.
**PCAP** : 캡처한 패킷들을 캡처 시각 등의 정보와 함께 저장한 파일이다.

>**읽기 vs 분석** : 10개의 패킷이 들어있는 PCAP 파일을 하나 읽는 것은 패킷 10개의 내용을 읽는 것과 같다고 생각했다.

-> **파일을 읽는다**는 것은 저장된 패킷 데이터를 하나씩 꺼내는 것이고, **패킷을 분석한다**는 것은 꺼낸 데이터에서 출발지 IP, 목적지 IP 등의 의미를 해석한다는 의미이다. 따라서 읽기와 분석하기를 구분해야한다.

---
### 2-2. 패킷 내부 구조
**header** : 데이터를 해석하는 데 필요한 정보를 담은 부분이다.

| 헤더         | 설명                            |
| ---------- | ----------------------------- |
| Ethernet   | 같은 링크에서 프레임을 전달하는 데 쓰는 MAC 주소 |
| IP         | 출발지·목적지 IP 주소                 |
| TCP 또는 UDP | 통신을 구분하는 출발지·목적지 **포트 번호**    |

**포트번호** : 한 컴퓨터 안에서 통신을 구분하는 번호이다.
```
192.0.2.10:53000 → 192.0.2.20:443  여기서 53000, 443이 포트번호이다.
```
**필드(field)** : 헤더 안에서 각각의 정보를 담는 항목이다.

|IP 헤더의 필드|의미|예시|
|---|---|---|
|출발지 IP|패킷을 보내는 쪽의 IP 주소|`192.0.2.10`|
|목적지 IP|패킷을 받는 쪽의 IP 주소|`192.0.2.20`|

---
### 2-3. PCAP 파일 구조
```
파일 전체 헤더
패킷 1 기록 헤더 → 패킷 1 데이터
패킷 2 기록 헤더 → 패킷 2 데이터
...
```
**파일 전체 헤더:** 파일 형식 등 파일 전체에 적용되는 정보를 담고 있다.

**패킷 기록 헤더:** 해당 패킷의 **캡처 시각과 저장된 길이** 등을 담고 있다.
> 패킷을 차례대로 꺼내려면 패킷 하나가 끝나는 위치가 어디인지 알아야한다. 따라서 프로그램은 각 패킷의 저장된 길이에 대한 정보를 알아야하고, 그 정보를 저장하고 있는 것이 바로 패킷 기록 헤더이다.

**패킷 데이터:** Ethernet·IP 등의 헤더와 실제 데이터가 들어 간다.

프로그램은 PCAP 파일에서 패킷을 하나씩 읽을 때 다음 순서를 반복한다.
```
파일 전체 헤더 확인
→ [패킷 기록 헤더 → 저장된 길이 확인 → 패킷 데이터 읽기 → 길이 검증] 반복
```

출발지 IP주소 읽기 단계까지 세분화하면 다음과 같다.
```
패킷 데이터 읽기 → 길이 검증 → Ethernet 헤더 분석 → IP 헤더 분석
                                                        └ 출발지 IP 확인
```

> 패킷안에 IP 헤더가 있는지 모르면?
-> Ethernet 헤더에는 **EtherType**이라는 필드가 있다. 이 필드는 뒤에 이어지는 데이터가 IPv4인지, IPv6인지, ARP인지 등을 구분하는 표시한다. ip 헤더 유무에 대한 정보가 없을때는 EtherType필드를 먼저 확인한 뒤 알맞은 방식으로 분석해야한다.

즉, EtherType을 확인하는 이유는 뒤의 데이터를 어떤 형식으로 읽어야 하는지 결정하기 위해서다.

```
Ethernet 헤더
  └ EtherType 확인
       ├ IPv4 → IPv4 형식으로 분석
       ├ IPv6 → IPv6 형식으로 분석
       └ ARP  → ARP 형식으로 분석
```

- **IP 주소:** 네트워크에서 출발지와 목적지를 지정하는 주소
- **MAC 주소:** Ethernet에서 같은 링크에 있는 장치로 데이터를 전달할 때 사용하는 주소

| 용어       | 의미와 역할                                                          | 예시                           |
| -------- | --------------------------------------------------------------- | ---------------------------- |
| **IPv4** | IP 버전 4. 32비트 주소를 사용한다.                                         | `192.0.2.10`                 |
| **IPv6** | IP 버전 6. 더 넓은 128비트 주소 공간을 사용한다.                                | `2001:db8::10`               |
| **ARP**  | 같은 IPv4 네트워크에서 **다음에 전달할 상대의 IP 주소에 대응하는 MAC 주소**를 알아내는 프로토콜이다. | “이 IP를 가진 장치의 MAC 주소가 무엇인가?” |

> EtherType이 ARP라면, ARP와 IPv4의 데이터 배치가 다르기때문에 그 데이터를 IPv4 형식으로 읽으면 안된다.

---
## 3. 프로그램 구현
프로그램은 **PCAP 파일 읽기 → 패킷 헤더 분석 → 결과 집계 → 출력** 순서로 동작한다.

 **주요 함수**

| 함수               | 역할                               |
| ---------------- | -------------------------------- |
| `read_packets()` | 파일 형식 확인 및 데이터를 순서대로 읽는 역할이다.    |
| `parse_packet()` | 패킷의 헤더를 분석해 주소·포트·프로토콜 등을 추출한다.  |
| `analyze()`      | 각 패킷의 분석 결과를 모으고 프로토콜별 개수를 집계한다. |
| `main()`         | 실행 인자를 받아 분석을 시작하고 결과를 출력한다.     |

---
### 3-1. PCAP 파일 읽기
`read_packets()`는 파일 전체 헤더에서 매직 넘버, 버전, 링크 계층 형식을 확인한다.
**매직 넘버** :  파일 형식과 바이트 해석 방식 등을 구분하는 값이다.
*이번 프로그램은 classic PCAP 2.4와 Ethernet 형식만 지원한다.*

이후 패킷마다 16바이트의 기록 헤더를 읽고, 저장된 길이만큼 데이터를 꺼낸다.

```python
seconds, fraction, captured, original = struct.unpack(
    endian + 'IIII', record
)
data = stream.read(captured)

if len(data) != captured:
    raise ValueError('Truncated PCAP packet data')
```

`captured`는 파일에 저장된 패킷 데이터의 길이다. 실제 읽은 길이가 이 값보다 짧으면 파일이 불완전하므로 분석을 중단한다.

---
### 3-2. 패킷 헤더 분석

`parse_packet()`를 통해 먼저 Ethernet 헤더를 읽고, EtherType을 확인한다.

```python
eth = dpkt.ethernet.Ethernet(data)

if eth.type != dpkt.ethernet.ETH_TYPE_IP:
    return dict(
        row,
        protocol='OTHER',
        note='Unsupported EtherType'
    )
```

IPv4라면 IP 헤더의 출발지·목적지 주소와 Protocol 필드를 확인한다. Protocol 값에 따라 TCP는 `6`, UDP는 `17`, ICMP는 `1`로 구분한다.

이번 구현에서 지원하지 않는 프로토콜과 IPv4 조각은 `OTHER`로 분류하고, 불완전하거나 잘못된 헤더를 발견한 경우에는 `ERROR`로 기록한다.

---
### 3-3. 통계 집계와 결과 출력

`analyze()`함수를 사용해서 각 패킷을 분석한 뒤 결과를 저장하고, 해당 분류의 개수를 증가시킨다.

```python
packets.append(row)
counts[row['protocol']] += 1
```

각 패킷은 `TCP`, `UDP`, `ICMP`, `OTHER`, `ERROR` 중 하나로 집계된다. 마지막으로 `main()`에서 패킷별 분석 결과와 전체 통계를 출력한다.

패킷은 파일에서 순서대로 읽지만, 분석 결과는 메모리에 모아 둔다.

---

## 4. 실행 결과 와 통신 해석

### 4-1. 실행 결과
전체 실행 결과는 다음 사진과 같다.
![PCAP 분석 프로그램 실행 결과](/assets/img/posts/pcap-file-analysis/execution.png)

---

### 4-2. 패킷 한 줄 읽기
```
src_ip:   192.0.2.10
src_port: 53000
dst_ip:   192.0.2.20
dst_port: 443
protocol: TCP
```
출발지 IP:포트 → 목적지 IP:포트, 프로토콜
**192.0.2.10 : 53000  ->  192.0.2.20 : 443 , TCP**

---
### 4-3. Ethernet·IP 헤더 확인

| 출력 항목                 | 들어 있는 헤더 |
| --------------------- | -------- |
| `ethertype: "0x0800"` | Ethernet |
| `ip_protocol: 6`      | IPv4     |

Ethernet·IP 헤더를 확인하여, 뒤에 이어지는 데이터의 프로토콜 정보를 확인할 수 있었다. 이 정보를 통해 데이터를 알맞은 형식으로 해석할 수 있다.

---
### 4-4. TCP 통신 분석 — 1~3번
#### 1번 패킷
```
192.0.2.10:53000 → 192.0.2.20:443
protocol: TCP
flags: 2 (= SYN)
```
패킷 내용을 해석해보면 , 192.0.2.10:53000 에서 192.0.2.20:443 으로 TCP 연결 시작을 요청한다는 걸 알 수 있다.

#### 2번 패킷
```
192.0.2.20:443 → 192.0.2.10:53000
flags: 18 (= SYN + ACK)
```
- **ACK:** 앞서 받은 연결 시작 요청을 확인하는 표시이다.
- **SYN:** 자신도 연결을 위한 초기 순서 번호를 알리는 표시이다.
이번엔 송수신이 반대로 바뀌었다.

#### 3번 패킷
```
192.0.2.10:53000 → 192.0.2.20:443
flags: 16 (= ACK)
```
첫 요청을 보낸 쪽에서 상대방의 응답을 확인한다.

이 1~3번 패킷의 과정을 **3-way handshake** 라고 한다.

| 패킷  | 방향          | 플래그       | 의미                      |
| --- | ----------- | --------- | ----------------------- |
| 1   | `.10 → .20` | SYN       | 연결 시작 요청                |
| 2   | `.20 → .10` | SYN + ACK | 요청 확인 및 자신의 연결 준비 정보 전달 |
| 3   | `.10 → .20` | ACK       | 상대의 준비 정보 확인            |

---
### 4-5. UDP 통신 분석 — 4~5번

```
4번: 192.0.2.10:54000 → 192.0.2.20:9999, UDP
5번: 192.0.2.20:9999  → 192.0.2.10:54000, UDP
```
**UDP** : TCP와 같은 연결 수립 절차 없이 데이터를 보내는 전송 프로토콜이다.
두 패킷의 출발지와 목적지 IP·포트가 서로 반대이므로, 양방향으로 데이터가 전송되었다는 것을 알 수 있다.

---
### 4-6. ICMP 통신 분석 — 6~7번

| 패킷  | 방향          | Type / Code |
| --- | ----------- | ----------- |
| 6   | `.10 → .20` | `8 / 0`     |
| 7   | `.20 → .10` | `0 / 0`     |

**ICMP** : IP 통신의 오류나 상태 등을 알리는 프로토콜이다.
6번 패킷은 Echo 요청, 7번 패킷은 Echo 응답을 하고 있다.
여기서 **Type**은 ICMP 메시지 종류, **Code**는 그 종류 안의 세부 구분이다.

---
### 4-7. 미지원 패킷 처리 — 8번

```
"ethertype": "0x0806"
"protocol": "OTHER"
"note": "Unsupported EtherType"
```

| 분류      | 의미                          |
| ------- | --------------------------- |
| `OTHER` | 이번 구현의 분석 범위 밖              |
| `ERROR` | 패킷을 분석하면서 불완전한 구조 등의 오류를 발견 |

8번 패킷의 EtherType은 `0x0806`으로 ARP에 해당한다. 이번 구현은 ARP 내부 분석을 지원하지 않아  결과가 `OTHER`로 나왔다.

### 4-8. 전체 통신 흐름 정리

전체 통신 흐름을 요약하자면 , TCP 패킷에서는 연결을 준비하는 3-way handshake를 관찰했고, UDP 패킷에서는 두 끝점 사이의 양방향 전송을, ICMP 패킷에서는 Echo 요청과 응답을 확인했다. 또한 ARP 패킷은 구현의 지원 범위 밖이어서 OTHER로 분류되었다.

## 5. 프로토콜별 통계와 검증

![TShark 비교 및 입력 검증 결과](/assets/img/posts/pcap-file-analysis/verification.png)

| 검사                                    | 결과      |
| ------------------------------------- | ------- |
| 샘플의 전체 개수와 프로토콜별 통계                   | 예상값과 일치 |
| TShark와 IP·포트·프로토콜·TCP 플래그·ICMP 필드 비교 | 일치      |
| 잘린 PCAP 및 미지원 PCAPNG 입력               |  거부     |

전체 8개 패킷은 TCP 3개, UDP 2개, ICMP 2개, OTHER 1개로 집계되었다. OTHER는 분석 범위 밖인 ARP 패킷이며, 분석 중 발견된 패킷 오류는 0개였다. 각 분류의 합은 전체 패킷 수와 일치했다.
