## 1.Part I: Whetting Your Appetite - Introduction to Debugging

이 챕터의 핵심은 **버그가 발생했을때, 코드를 감으로 고치지말고, 가설과 실험으로 버그의 원인을 좁혀나가자**는 것이다. 

### 1-1. 챕터 내용 흐름 

```
HTML 태그를 지우는 함수를 만든다
          ↓
일부 입력에서 잘못된 결과가 나온다
          ↓
변수를 이용해 함수의 동작을 이해한다
          ↓
원인 가설을 세우고 작은 입력으로 시험한다
          ↓
assert로 내부 상태와 실행 경로를 확인한다
          ↓
결함을 찾아 수정한다
          ↓
기존 테스트와 새 테스트로 다시 검증한다
```

책에서는 `remove_html_markup()` 라는 HTML 태그를 지우는 함수를 예시로 사용한다. 처음에는 `tag`, `out`을 사용하고, 따옴표 처리를 위해 `quote`를 추가했다.

| 변수      | 의미                 |
| ------- | ------------------ |
| `tag`   | 지금 태그 내부에 있는가?     |
| `quote` | 태그 안의 따옴표 구간에 있는가? |
| `out`   | 지금까지 남긴 글자         |

---
### 1-2. 버그가 드러나는 과정 

책에서는 버그가 드러나는 과정을 결함, 잘못된 내부 상태, 실패로 구분한다.

```
사람의 실수
    ↓
코드의 결함
    ↓
실행 중 잘못된 내부 상태
    ↓
외부에서 확인되는 실패
```

---

### 1-3. 버그 원인 좁히기

| 입력 내용          | 기대 결과   | 결함 버전의 결과    |
| -------------- | ------- | ------------ |
| `<b>foo</b>`   | `foo`   | `foo`        |
| `<b>"foo"</b>` | `"foo"` | `foo`        |
| `"<b>foo</b>"` | `"foo"` | `<b>foo</b>` |

**`"<b>foo</b>"`를 넣었는데 `<b>foo</b>`가 나오는 이유** : 
```python
c == '"' or (c == "'" and tag)
```
이 코드를 해석해보면 조건이 참일때 quoto의 값을 반대로 바꾼다는 의미이다. c에 큰따옴표가 들어가 있고, 초기상태가 tag=false, quoto=false라면, 위의 조건식이 참이된다. 

```python
if c == '<' and not quote:
    tag = True
```
그 뒤, 현재 quoto=true 이기 때문에, true and false 결과 false가 된다. 

```python
elif not tag:
    out = out + c
```
현재 tag=false이라, `not tag`가 참이므로 **지워져야 할 `<`가 출력에 추가**된다. 이때 따옴표 처리 분기가 실행됐으므로 뒤의 `elif not tag`는 실행되지 않는다. 따라서 맨 앞 큰따옴표는 출력에 추가되지 않는다.

이후에도 `quote`는 `True`, `tag`는 `False`로 유지되어 `b`, `>`와 뒤의 문자들이 출력에 추가된다. 마지막 큰따옴표에서는 따옴표 처리 분기가 실행되어 `quote`가 다시 `False`로 바뀌고, 큰따옴표 자체는 출력되지 않는다. 따라서 최종 결과는 `<b>foo</b>`가 된다.

---

### 1-4. 수정 후 검증하기 

버그를 수정한 뒤에 회귀 테스트를 거치는 과정까지 디버깅에 포함된다. 수정 후에는 실패했던 입력뿐 아니라 기존에 정상적으로 처리하던 입력도 다시 확인해야 한다.
*회귀 테스트〔regression test〕 : 이후 변경으로 이미 고친 문제가 다시 발생하는지 확인하는 테스트이다.*

```
# 수정 전
c == '"' or c == "'" and tag

# 수정 후
(c == '"' or c == "'") and tag
```

아까 예시의 경우 두 따옴표 조건을 괄호로 묶어, 태그 안에 있을 때만 `quote`가 바뀌도록 수정한다. 이제 맨 앞 큰따옴표에서는 `tag`가 `False`이므로 `quote`가 바뀌지 않는다. 따라서 다음 `<`를 태그 시작으로 인식할 수 있다.

![디버거 실행 결과](/assets/img/posts/python-debugger/execution-1.png)
코드 수정 후 다시 같은 입력으로 코드를 실행해보았고, 수정 후 모두 기대값과 일치한 것을 확인했다.

## 2. Part II: Observing Executions - Tracing Executions

앞 장에서 원인 가설을 세우는 방식과 관련된 내용을 다루었고, 챕터2에서는 **실행 위치와 변수 변화를 관찰하는 방법** 에 대해서 나온다. 

### 2-1. 챕터 내용 흐름

```
Python에 추적 함수를 등록한다
          ↓
함수 호출·줄 실행·반환 이벤트를 받는다
          ↓
프레임에서 실행 위치와 변수 값을 읽는다
          ↓
Tracer 클래스로 추적 기능을 묶는다
          ↓
소스 코드와 달라진 변수만 출력한다
          ↓
조건을 만족하거나 값이 변할 때만 출력한다
          ↓
추적 비용과 다른 구현 방식을 살펴본다
```

---

### 2-2. 추적 함수와 프레임으로 실행 정보 확인하기

간단한 실행 코드의 경우, 실행 중간 변수 값의 변화를 확인하고 싶다면 print()문을 사용한다. 하지만 코드가 복잡해지고, 확인 해야 할 값이 많아질 수 록 print()를 사용하는 것이 오히려 코드를 더 복잡하게 만들고, 번거로워질 수 있다. 

책에서는 `sys.settrace()`를 이용해 추적 함수를 사용하는 예시를 보여준다. `sys.settrace()` 는 python에 관찰 함수를 등록하는 방식으로, 줄 실행 등의 이벤트가 생길 때 관찰 함수를 호출한다. 그 함수에서 실행 위치와 변수 값을 읽을 수 있다. 

추적 함수는 다음 3가지 정보를 받는다.

|정보|의미|
|---|---|
|`frame`|지금 실행 중인 함수 호출의 상태|
|`event`|어떤 사건이 발생했는지|
|`arg`|사건에 따라 전달되는 추가 정보|

`frame` 은 함수 호출 하나의 실행 정보를 담는 객체이다. 

|속성|의미|
|---|---|
|`frame.f_lineno`|현재 줄 번호|
|`frame.f_locals`|현재 지역변수|
|`frame.f_code.co_name`|현재 함수 이름|

또한, 대표적인 이벤트는 다음과 같다. 

|이벤트|발생 시점|관찰할 내용|
|---|---|---|
|`call`|함수에 진입할 때|어떤 함수가 호출됐는가|
|`line`|해당 줄을 실행하기 직전|어디까지 실행됐고 변수는 무엇인가|
|`return`|함수에서 반환할 때|어떤 값을 반환하는가|

**`line` 이벤트에서 보이는 값은 해당 줄을 실행하기 직전의 상태**이다.
`total += 1000` 줄의 `line` 이벤트에서는 덧셈 전 값을 보게 된다. `total`이 원래 `0`이었다면 이 시점에도 `0`이고, 해당 줄이 실행된 뒤의 이벤트에서 변경된 값을 확인할 수 있다.

---

### 2-3. Tracer로 추적 시작과 종료 관리하기

매번 추적을 켜고 끄는 코드를 작성하면, 함수 실행 중 오류가 발생해서 추적을 끄는 처리를 놓칠 수 있다. 따라서 책에서는 다음과 같이 `Tracer` 클래스를 활용한다.

예를 들어서, 추적을 시작하고 대상 함수를 실행한뒤 이전 추적 설정을 복원하는 코드가 있다. 여기서 '대상 함수 실행' 부분이 오류로 중단된다면 그 아래에 있는 코드인 '이전 추적 설정 복원' 부분에는 도달하지 못하게 된다. 책에서는 이런 문제를 해결하기 위해서 `with Tracer()` 을 사용해서 with문 안에서 오류가 생기더라도 종료 처리인 `__exit__()`를 거쳐 이전 추적 설정을 복원할 수 있게 한다. 

역할 정리 : `Tracer` - 컨텍스트 매니저
		  `__exit__()`- 이전 추적 설정 복원

---

### 2-4. 필요한 실행 정보와 변화 출력하기

매번 모든 변수 정보를 출력하면 같은 내용이 반복되고, 실행 기록이 많아질수록 필요한 정보를 찾기 어려워진다. 이번 챕터에서는 현재 소스코드 함수 호출·반환, 달라진 변수 값을 보여줄 수 있게 출력을 개선한다.

| 보여 주는 정보     | 필요한 이유                        |
| ------------ | ----------------------------- |
| **현재 소스 코드** | 줄 번호뿐 아니라 어떤 문장을 실행하려는지 알기 위해 |
| **함수 호출·반환** | 어떤 함수에 들어갔고 무엇을 반환했는지 알기 위해   |
| **달라진 변수 값** | 바뀌지 않은 정보를 반복해서 읽지 않기 위해      |

변수 변화는 이전에 관찰한 값과 현재 값을 비교해서 확인한다. 이때 현재 표시된 줄은 실행 직전이기 때문에, 관찰한 변수의 변화는 앞서 실행한 문장의 결과일 수 있다.

책에서는 필요한 순간의 기록만 출력하는 방법도 보여준다.

|방식|사용하는 클래스|출력 조건|
|---|---|---|
|조건부 추적|`ConditionalTracer`|지정한 조건이 참인 동안 출력|
|값 변화 감시|`EventTracer`|감시하는 표현식의 값이 달라졌을 때 출력|

예를 들어서 `total >= 1000`이라는 조건부 추적은 `total`이 1000 이상인 동안 출력하고, `total`의 값 변화 감시는 이전에 관찰한 값과 달라졌을 때 출력한다. 같은 `total`을 확인하더라도 **조건이 참인지 확인하는 것과 값이 바뀌었는지 확인하는 것의 차이**가 있다.

---

### 2-5. 추적 비용과 코드 계측

필요한 기록만 출력하더라도 추적 비용은 남아있다. 조건부 추적의 경우 조건이 거짓이면 출력을 생략하지만, 추적 함수를 호출하고 조건을 검사하는 과정은 실행되기 때문에 반복문이 많이 돌수록 추가 작업도 쌓이게 된다.

```
줄 실행 직전
    ↓
추적 함수 호출
    ↓
조건 검사
    ├─ 참 → 출력
    └─ 거짓 → 출력 생략
```

대안:  **코드 계측(instrumentation)** - 관찰할 위치에 추적 코드를 미리 넣는 것을 의미한다.

|방식|관찰 방법|특징|
|---|---|---|
|앞서 만든 동적 추적|실행 이벤트마다 추적 함수를 호출해 검사|관찰 조건을 유연하게 정할 수 있음|
|특정 위치에 코드 삽입|미리 정한 위치에서 관찰 코드를 실행|다른 위치에서 반복하는 추적 작업을 줄일 수 있음|

이 경우 미리 정한 위치에서 관찰 코드를 실행하기 때문에 다른 위치에서 반복되는 추적 작업을 줄일 수 있지만 관찰할 위치를 미리 정해야 하기 때문에, 변수가 어디서 바뀌는지 모르는 경우에는 적용하기 어렵다.

## 3. Part II: Observing Executions - How Debuggers Work

이번에는 추적 기능에 **실행을 멈추고 사용자 명령을 받는 기능**을 더해 디버거로 확장한다.

### 3-1. 챕터 내용 흐름

```
실행 이벤트와 프레임 정보를 받는다
          ↓
멈춰야 하는지 판단한다
          ↓
현재 위치와 변수 상태를 표시한다
          ↓
사용자 명령을 받아 담당 메서드에 연결한다
          ↓
상태를 조회하거나 실행을 재개한다
          ↓
중단점으로 원하는 위치에서 다시 멈춘다
```

---
### 3-2. 추적기에서 대화형 디버거로 확장하기

**추적기[Tracer]** : 실행 정보를 출력한 뒤 프로그램을 계속 진행시킨다.
**대화형 디버거[interactive debugger]** :  추적기에 사용자의 명령을 기다리는 과정을 추가한다.

```
추적기:
실행 이벤트 → 추적 함수 호출 → 정보 출력 → 실행 계속

대화형 디버거:
실행 이벤트
    ↓
멈춰야 하는지 판단
    ↓
현재 위치와 변수 표시
    ↓
사용자 명령 기다리기
    ├─ 변수 조회 → 출력 후 다시 기다림
    └─ 실행 재개 → 추적 함수에서 돌아가 실행 계속
```

이때 추적 함수가 명령 입력을 기다리는 동안에는 관찰 중인 실행 흐름도 다음으로 진행하지 못하기 때문에, 사용자는 멈춘 상태에서 변수를 확인하거나 실행을 이어갈 수 있다.

---

### 3-3. 사용자 명령 처리하기

디버거는 사용자 입력을 명령어와 인자로 나누고, 해당 명령을 처리하는 메서드에 연결한다. 예를 들어서 `print total`을 입력하면 명령어인 `print`와 인자인 `total`로 나눈다.

|부분|내용|의미|
|---|---|---|
|명령어|`print`|어떤 작업을 할 것인가|
|인자〔argument〕|`total`|무엇을 대상으로 할 것인가|

```
사용자 입력           연결되는 메서드
print total      →    print_command("total")
step             →    step_command("")
continue         →    continue_command("")
```

**명령 분배기(command dispatcher)** : 입력한 명령어를 해석하고 해당 명령을 처리하는 메서드로 연결하는 부분이다.

명령을 처리한 뒤에는 종류에 따라 다시 입력을 기다리거나 실행을 재개한다. `print`, `list`는 결과를 출력한 뒤 다시 명령을 기다리고, `step`, `continue`는 다음 정지 조건을 설정한 뒤 입력 대기를 끝내고 실행을 이어간다.

```
명령 처리
    ├─ print, list 같은 조회 명령
    │      → 결과 출력 → 다시 명령 대기
    │
    └─ step, continue 같은 진행 명령
           → 다음 정지 조건 설정 → 입력 대기 종료 → 실행 재개
```

---

### 3-4. 변수와 소스 코드 확인하기

|명령|역할|처리 후 상태|
|---|---|---|
|`print`|대상 프레임에서 변수나 표현식의 값 확인|계속 정지|
|`list`|소스 코드와 현재 위치 표시|계속 정지|

이때 `print`는 디버거 자신의 변수가 아니라 **멈춘 대상 함수의 실행 문맥**에서 값을 확인해야 한다. 예를 들어서 `print total`을 입력했다면 디버거 내부의 `total`이 아니라, 현재 멈춰 있는 대상 함수의 `total` 값을 확인하는 것이다.

---

### 3-5. 중단점으로 실행 위치 지정하기

매번 `step`으로 한 단계씩 이동하면 오래 걸린다. 따라서 조사할 위치에 **중단점(breakpoint)** 을 설정하고 `continue`로 실행을 재개한다.

*중단점은 프로그램이 지정한 실행 위치에 도달하면 멈추도록 하는 설정이다.*

|명령|역할|
|---|---|
|`break LINE`|지정한 줄에 중단점 설정|
|`continue`|실행 재개 후 중단 조건을 만나면 정지|
|`delete LINE`|지정한 줄의 중단점 삭제|

```
line 이벤트를 받음
        ↓
현재 줄이 저장된 중단점인가?
    ├─ 예 → 명령 입력 대기
    └─ 아니오 → 다른 정지 조건이 없으면 실행 계속
```

이때 **중단점에 도달한 줄은 실행하기 직전**이다. `break`와 `delete`는 설정만 바꾸므로, 대상 실행을 이어 가려면 `continue` 같은 진행 명령이 필요하다.

## 4. 디버거 구현 과정

앞에서 정리한 내용을 바탕으로 Python 디버거를 만들었다. 기본 디버거 구조를 먼저 구현하고, 세 번째 챕터인 How Debuggers Work의 Exercise 2 기능을 추가했다. 그 후 예외가 발생했을 때 실행을 멈추고 상태를 확인할 수 있도록 확장했다.

> 구체적인 코드는 **AI가 작성했다.** 

>모든 코드 설명을 블로그에 다 쓰기보단, 실행 정보 받기와 추가 기능 코드 설명에 집중했다.

### 4-2. 실행 정보 받기 코드 설명

디버거 코드에서 가장 중요한 부분이 **실행 정보 받기**와 관련된 코드이다. 디버거의 나머지 모든 기능들은 전부 실행 정보를 받은 후 동작하기 때문이다. 

앞에서 정리한 추적 함수와 프레임을 이용해서 대상 함수의 실행 정보를 받도록 구현했다. 먼저 기존 추적 설정을 저장하고, 디버거의 `_trace`를 추적 함수로 등록한다.

```
self.previous = sys.gettrace()
self.active = True
sys.settrace(self._trace)
```

이때 기존 설정을 저장하는 이유는 디버깅이 끝난 뒤 이전 상태로 복원하기 위해서이다. 등록된 `_trace()`는 Python이 전달하는 `frame`, `event`, `arg`를 받는다.

```
def _trace(self, frame, event, arg):
```

예를 들어서 `line` 이벤트가 발생하면 `frame.f_lineno`로 실행할 줄 번호를 확인하고, `frame.f_locals`로 지역변수를 확인한다. 앞에서 살펴본 것처럼 이때의 값은 **해당 줄을 실행하기 직전의 상태**이다.

**관찰 대상 구분**

디버거 코드와 대상 함수의 실행이 섞이지 않도록 디버거 자신의 파일은 관찰에서 제외한다.

```
if not self.active or frame.f_code.co_filename == __file__:
    return None
```

처음 관찰한 대상 함수의 프레임은 `root`에 저장하고, 이후에는 `f_back`으로 호출자를 따라가며 대상 함수에서 이어진 호출인지 확인한다.

```
if self.root is None:
    if event != 'call':
        return None
    self.root = frame

ancestor = frame
while ancestor is not None and ancestor is not self.root:
    ancestor = ancestor.f_back

if ancestor is None:
    return None
```

현재 프레임에서 호출자를 따라갔을 때 `root`를 만나면 관찰 대상이고, 끝까지 찾지 못하면 제외한다. 이를 통해 대상 함수뿐 아니라 **대상 함수가 호출한 함수도 함께 관찰**할 수 있다.

**정지 정보 저장**

관찰 대상이면 중단점과 실행 모드 등을 검사하고, 멈출 조건에 해당하면 현재 정보를 저장한 뒤 명령 입력을 기다린다.

```
if reasons or reached:
    self.frame, self.event, self.arg = frame, event, arg
    self.interact(reasons)
```

`reasons`는 중단점·감시점·예외 등의 정지 이유이고, `reached`는 진행 명령이 정한 정지 지점에 도달했는지를 나타낸다. 저장한 정보는 현재 위치와 변수를 보여줄 때 사용하고, `interact()`에서 명령 입력을 기다리는 동안 대상 실행도 멈춰 있게 된다.

### 4-3. 추가 기능: 예외 발생 시 정지

추가 기능은 예외가 발생했을 때 실행을 멈추고 변수와 호출 위치를 확인하는 기능`exceptions on|off` 을 골랐다. 디버거의 목적이 코드가 예상과 다른 동작을 했을때, 그 원인을 찾는 것인데, 예외가 이 목적에 가장 적합하다고 생각했기 때문이다. 코드를 짤 때 예외가 발생하는 것은 너무나 자주 있는 일이라 이번 디버거 기능 구현에 꼭 추가하고 싶었다. 

먼저 명령어는 다음과 같다.

| 명령               | 동작            |
| ---------------- | ------------- |
| `exceptions on`  | 예외 발생 시 정지    |
| `exceptions off` | 예외 정지 해제. 기본값 |
| `exceptions`     | 현재 설정 표시      |

**예외 정지 설정**

```
if argument:
    self.exceptions = argument == 'on'
```

이 코드를 해석해보면 `on`을 입력했을 때 조건이 참이므로 `self.exceptions`에 `True`를 저장하고, `off`를 입력하면 `False`를 저장한다. 인자가 없다면 기존 설정을 유지하고, 잘못된 인자는 이 코드 앞에서 검사하기 때문에 사용법을 안내한 뒤에 따로 설정을 바꾸지 않아도 된다. 

**예외 이벤트 처리**

```
if event == 'exception' and self.exceptions:
    reasons.append(f'{arg[0].__name__}: {arg[1]}')
```

앞에서 다룬 추적 이벤트 중 `exception`을 이용해서 예외 발생을 확인하고, 현재 `self.exceptions`가 `True`라면 `arg[0]`인 예외 타입과 `arg[1]`인 예외 객체에서 이름과 메시지를 가져와 정지 이유에 추가한다.

```
if reasons or reached:
    self.frame, self.event, self.arg = frame, event, arg
    self.interact(reasons)
```

예외가 정지 이유에 추가되었기 때문에 기존 정지 처리에서 현재 실행 정보를 저장하고 명령 입력을 기다리게 된다. 이때 예외 자체를 없애는 것은 아니므로 `continue`를 입력하면 대상 프로그램의 원래 예외 처리가 이어지고, `try/except`로 처리할 예외도 발생한 시점에는 멈춰서 변수와 호출 위치를 확인할 수 있다.

## 5. 예외 정지 코드 실행결과 

![디버거 실행 결과](/assets/img/posts/python-debugger/execution-2.png)

예외 정지 기능을 시험하기 위해 `demo.py`를 실행했다. 
사용한 예제 : `[1000, 2000, 3000]`의 각 값에 0.8을 곱해 합산하고, 이후 일부러 0으로 나누기 -> 예외 발생 

`exceptions on`으로 예외 정지를 켜고 `continue`를 입력하니까 `calculate()`의 13번 줄에서 `ZeroDivisionError`가 출력되며 멈췄다. 이 상태에서 `where`로 현재 위치를 살펴보고, `print price`를 입력하면 지역변수 값이 `3000` 이라고 나온다. 

다시 `continue`를 입력하면 대상 코드의 `except` 처리가 되고, 최종 결과 `4800.0`이 출력됐다. 결론적으로 **예외가 발생한 순간에 실행을 멈추고, 변수와 위치를 살펴본 뒤 다시 진행하는 흐름**을 볼 수 있었다.

## 6. 느낀 점 

디버거 라는 것을 항상 기술로써 활용해보기만 했었는데, 이걸 직접 원하는 기능까지 추가해서 만들어보니 흥미로웠다. 디버거 기능에서 실행 정보가 얼마나 중요한 역할을 하는지에 대해 머릿속으로 체계화 해서 정리할 수 있게 되었다. 특히 실행 이벤트와 프레임 정보가 중단점, 변수 조회, 예외 정지에 어떻게 쓰이는지 정리하면서 디버거의 동작을 더 구체적으로 이해할 수 있었다.
또한, 꼭 디버거가 아니더라도, 자신이 평소 자연스럽게 사용하던 프로그램을 직접 만들어보는 경험은 정말 큰 도움이 된다는 걸 느꼈다.
